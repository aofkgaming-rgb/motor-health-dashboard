# MHM Dashboard — Change Report

**Project:** Edge AI Motor Health Monitor with Revolution Jitter Analysis (MHM)
**Date:** 25 October 2026
**Scope:** Trimmed scope agreed on 25 Oct 2026 (see §15). Hardware not yet connected; all live-data behaviour tested with a script that sends packets in Board B's exact format.

Status labels used below:
**Completed and Tested** · **Implemented but Not Fully Tested** · **Pending External Integration** · **Not Implemented**

---

## 1. Executive summary

The dashboard was showing a different machine (15 kW, 1800 rpm, 10 kHz sampling), vibration in velocity units with ISO severity limits that do not apply to an accelerometer, hard-coded "AI confidence" numbers, and a server that overrode the device's health decision. It also accepted any user ID.

It has been rebuilt around the real system: the server now **stores and displays what Board B decides** and never recalculates it, uses **one data format end to end** (Board B JSON = SD-card CSV = dashboard export), keeps **demo data strictly separate and labelled**, and explains every parameter through ⓘ popovers. All standards labels were removed on request.

## 2. Problems in the previous dashboard

| Problem | Effect |
|---|---|
| Motor shown as 15 kW / 20 HP, 1800 rpm, 10 kHz sampling, 1024-point FFT | Contradicted the real bench motor (0.75 kW, 1400 rpm, 3200 Hz, no FFT) |
| Vibration in mm/s with ISO 10816 limits | ADXL345 measures acceleration (g); velocity limits do not apply |
| AI confidence fixed at 96.4 / 91.8 / 95.2 % | Not model output |
| Server and browser both re-computed the health class | Overrode the on-device decision — wrong architecture |
| `POST /api/motor/telemetry` had no key | Anyone with the URL could push readings |
| Simulator kept running during real data | Demo and real values mixed |
| 1h/6h/24h/7d history generated by formula | Not stored data |
| Login accepted any ID ≥ 3 characters | Not real authentication |
| Browser fell back to saved user when token was rejected | Expired sessions still showed the dashboard |
| ESP32 popup showed MPU6050 / DS18B20 / PT100 | Wrong sensors |
| WebSocket and control endpoints required no sign-in | Data visible without logging in |
| No phase currents, z-scores, class or device status | Real outputs of the system missing |

## 4. The six parameters

Units and conventions are defined once in `src/shared/contract.ts` and explained in `src/content/info.ts`.

| Parameter | Field | Unit | Definition shown | Status |
|---|---|---|---|---|
| RMS vibration | `rms_g` | g | √((1/N)Σ(xᵢ−x̄)²), N = 3200 (1 s), mean removed | Completed and Tested (display) · Pending firmware |
| Peak value | `peak_g` | g | max\|xᵢ−x̄\| over 1 s | Completed and Tested (display) · Pending firmware |
| Crest factor | `crest` | ratio | Peak / RMS | Completed and Tested (display) · Pending firmware |
| Kurtosis | `kurtosis` | — | Pearson, Gaussian = 3.0 (not excess) | Completed and Tested (display) · Pending firmware |
| Revolution jitter | `jitter_pct` | % | σ(T)/mean(T)×100, 50 revolutions, Hall pulses | Completed and Tested (display) · Pending firmware |
| Temperature rise rate | `temp_rise_c_min` | °C/min | ΔT/Δt over 6 MLX90614 samples | Completed and Tested (display) · Pending firmware |

Per-parameter status comes **only** from the z-score the device sends against its own 2-hour healthy baseline (warning |z| ≥ 3, critical ≥ 5 — stated as project defaults, not a standard). With no baseline the badge says "Not calibrated" or "No baseline value" — no invented thresholds.

## 5. Sensor and ESP32 integration

- Endpoint `POST /api/v1/telemetry`, header `X-Device-Key`, one row or `{ "rows": [...] }` (≤ 500, for re-sending the buffer after a Wi-Fi drop).
- Validation: numbers checked for type and plausibility; bad values stored as empty and flagged, never clipped or set to 0; invalid device time replaced by server time and flagged.
- Duplicate detection by `device_id + boot + seq`; out-of-order rows inserted in time order.
- Device status: Live < 15 s, Stale 15–60 s, Offline > 60 s, with alerts.

**Status: Pending External Integration.** Tested end to end with a script posting Board B-format packets (accepted, duplicates dropped, rejected row reported, live→stale→offline transitions, demo auto-stop). Board B firmware does not yet send these packets, and the real hardware has not been connected.

## 6. Edge AI architecture and deployment status

- Inference is described as running **on ESP32 Board B** (Random Forest, 50 trees, exported to C++). The dashboard displays the class, tree agreement (`votes/trees`, labelled as not a calibrated probability) and model id.
- Model id `rules` is shown as the rule-based fallback; validation metrics are shown as "Not available — training in progress".
- Jitter and temperature rise rate are shown as baseline-monitored, not model inputs (public datasets lack them).
- Class names are not fixed in the dashboard; it shows whatever label the device sends. The demo uses placeholder labels.

**Status: Pending External Integration.** Model not yet trained (CWRU + MaFaulDa) or deployed; class scheme to be fixed after training.

## 7. Historical storage

In server memory: every row for ~15 minutes, one row per 10 s for 24 hours, kept separately for device and demo sources. Render's free plan has no persistent disk, so history resets when the server restarts; the **SD card on Board B is the permanent record**. This is stated in the interface.

**Status: Completed and Tested** (in-memory). Persistent database: **Not Implemented** (outside trimmed scope).

## 8. Monthly reports and notifications

In-dashboard alerts are derived from device data: model output change, baseline-deviation change, sensor fault, data-quality flag, device online/offline, demo stopped by live data. A new class or severity must hold for **3 consecutive rows** before an alert is raised, so noise does not make alerts flap (verified: 4 alerts for a healthy→imbalance→healthy sequence instead of a continuous stream).

Monthly PDF reports, scheduled jobs and email: **Not Implemented** by decision — they need a scheduler, PDF generator and email service that the sleeping free server cannot run reliably. Monthly analysis is to be done offline in Python from the SD-card logs.

## 9. CSV export

- Columns (schema v1): `timestamp_utc, device_id, source, seq, rpm, jitter_pct, rms_g, peak_g, crest, kurtosis, temp_c, temp_rise_c_min, i_l1_a, i_l2_a, i_l3_a, class, vote_share, model, z_max, calibrated, quality`
- One row per record, header row, UTF-8, `,` separator, `.` decimal, CSV escaping, missing values empty (never 0), ISO-8601 UTC timestamps.
- Filters: range and source. File name contains device id (or `DEMO-DATA`), resolution, time and schema version. Sign-in required.
- Column definitions table on the History page.

**Test result:** exported 64 device rows; parsed with Python `csv`: 21 columns, only `source = device`, all numeric columns numeric, timestamps sorted, no duplicates. **Status: Completed and Tested.** Opening in Excel/MATLAB: **Implemented but Not Fully Tested** (format is standard; not opened in those programs here).

## 15. Known issues and limitations

- Server history resets on restart or redeploy (free plan, no disk).
- Alerts are kept in memory (last 300) and reset on restart.
- Demo values and demo class names are illustrative, not derived from the trained model.
- Phase-current imbalance is computed in the dashboard from the three device values.
- The free Render instance sleeps after ~15 min idle; the keep-alive ping uses most of the free monthly hours.

## 16. Remaining requirements

1. **Render:** add `DEVICE_KEY` (long random string) under Environment; until then ingestion returns 503.
2. **Board B firmware:** send the packet format shown on the Device page to `/api/v1/telemetry` with the same key; buffer rows while offline; log the same columns to SD.
3. **Board A firmware:** compute the six features with the definitions above (mean-removed RMS, Pearson kurtosis, 50-revolution jitter).
4. **Calibration:** 2-hour healthy run to produce baseline statistics and z-scores.
5. **Model:** train on CWRU + MaFaulDa, fix the class scheme, export to C++, send `cls`, `votes`, `trees`, `model`.
6. **Bench validation:** compare rpm, current (clamp meter) and temperature with references.
